# リポジトリ改善点

調査日: 2026-09-07
対象: `main` ブランチの JavaFX / SQLite アプリケーション

## 概要

基本的なCRUD機能、ファイル入出力、バックアップ、設定保存、テスト、CIまで実装されており、テンプレートとしての土台は整っています。一方で、データ量が増えた場合の処理、復元時のデータ保全、ドキュメントの追従性、UIとデータアクセスの責務分離に改善余地があります。

## 優先度の高い改善点

| 優先度 | 分類 | 根拠 | 改善案 |
| --- | --- | --- | --- |
| 高 | インポートの原子性 | `BasicWindowsApp#importMessages` は読み込んだメッセージを1件ずつ `MessageDao#insertMessage` しており、途中でエラーになると一部だけ登録された状態が残る | DAOに一括登録用トランザクションを追加し、全件成功時だけコミットする。失敗時はロールバックし、何件目で失敗したかを表示する |
| 高 | バックアップの整合性 | `BackupService#createBackup` はアプリ稼働中のSQLiteファイルを直接コピーする。書き込み中にバックアップすると、復元できない、または直近の更新を欠くバックアップになる可能性がある | SQLiteのバックアップAPIまたは読み取りトランザクションでスナップショットを取得してからアーカイブ化する。バックアップ作成前にDB処理を停止または排他する |
| 高 | 復元の安全性 | `BackupService#restoreBackup` は既存のDB・設定へ直接書き込み、途中で失敗した場合に元ファイルを戻さない | 一時ファイルへ展開し、DBの検証後に原子的に置換する。置換前のファイルを退避し、復元失敗時にロールバックできるようにする |
| 高 | 復元アーカイブの検証 | 復元処理はエントリ名の検査は行うが、DBと設定の重複エントリ、エントリサイズ、総展開サイズ、圧縮率を制限していない | 必須エントリを一意に要求し、許容サイズ・エントリ数を設定する。ZIP爆弾や異常に大きい入力を拒否する |
| 中 | UIスレッド上のDB処理 | 初期読み込み、追加、編集、削除、更新はJavaFXアプリケーションスレッドでDAOを呼び出すため、DBやデータ量が大きいと画面が固まる | DB操作を専用Executorへ移し、結果とダイアログ表示だけを `Platform.runLater` でUIスレッドへ戻す。処理中は該当操作を無効化する |
| 中 | 大量データの一括表示 | `MessageDao#getAllMessages` と `MessageFileService#read` は全件をメモリへ読み込む。TableViewにも全件を投入するため、データ量に比例してメモリと応答時間が増える | ページングまたは遅延読み込みを導入する。インポート・エクスポートはストリーム処理にし、件数上限や進捗を設ける |

## データ処理・エラー処理

| 優先度 | 分類 | 根拠 | 改善案 |
| --- | --- | --- | --- |
| 中 | CSV仕様の厳密性 | `MessageFileService#parseCsvLine` は引用符がフィールド先頭以外に現れるケースや、引用符終了後の文字列を厳密に拒否しない | CSV仕様に沿った状態検証を追加するか、実績のあるCSVライブラリを利用する。異常行の内容を安全に示す |
| 中 | テキスト形式の改行 | TEXT出力はメッセージごとに1行を書き出すため、本文に改行を含めると再インポート時に別メッセージへ分割される | 改行をエスケープする形式を定義するか、TEXT形式では改行を拒否する。仕様とテストで明示する |
| 中 | 入力値の制約 | `MessageValidator` は空白のみを拒否するが、本文の最大長や制御文字を制限していない | UI、インポート、DAOで共通の最大長・許容文字ルールを定義し、DB投入前に検証する |
| 中 | エラー時の状態復旧 | TableViewのインライン編集では、DB更新前にモデルを変更してから失敗時に再読み込みしている。再読み込み自体が失敗した場合、画面とDBの状態がずれる可能性がある | DB更新成功後にモデルを更新するか、更新前の値を保持して明示的に復元する |
| 低 | DBリソース管理 | `DatabaseManager#initializeDatabase` の `ResultSet` がtry-with-resourcesで管理されていない | `ResultSet` をtry-with-resourcesへ含め、接続・文・結果セットのライフサイクルを統一する |
| 低 | 失敗の可観測性 | `DatabaseManager#deleteDatabase` はIOExceptionを握りつぶして `false` のみ返す | 呼び出し側で扱える例外を返すか、少なくとも原因をログへ記録する。テスト用APIと本番APIを分離する |

## 設計・保守性

| 優先度 | 分類 | 根拠 | 改善案 |
| --- | --- | --- | --- |
| 中 | メインクラスの肥大化 | `BasicWindowsApp.java` が画面構築、イベント処理、非同期処理、ファイル操作、ダイアログ、グラフ更新をすべて担当している | `MessageView`、`MessageController`、ファイル操作コーディネーター、ダイアログ生成などへ分割し、UIテスト可能な境界を作る |
| 中 | 設定値の重複 | バージョンが `pom.xml` と `BasicWindowsApp.APP_VERSION` に重複している | Mavenのプロジェクトバージョンをリソースへフィルタリングして、表示値を一元化する |
| 低 | 不要な依存関係 | `pom.xml` は `javafx-fxml` を宣言しているが、FXMLファイルやFXMLローダーの利用は確認できない | FXMLを使わない方針なら依存関係を削除する。将来利用するなら採用理由をREADMEに記載する |
| 低 | 日時処理の旧API | `BasicWindowsApp` は `SimpleDateFormat` と既定タイムゾーンを使っている | `java.time` の `Instant`、`ZoneId`、`DateTimeFormatter` を使い、表示タイムゾーンを明示する |
| 低 | ウィンドウ位置の復元 | 保存済みの位置が現在のディスプレイ範囲外でもそのまま適用される | 起動時に画面の可視領域を確認し、範囲外の場合は中央配置または既定位置へ戻す |

## ドキュメント・CI

| 優先度 | 分類 | 根拠 | 改善案 |
| --- | --- | --- | --- |
| 高 | READMEの現状不一致 | READMEはJARを `0.1.0` と記載し、SQLiteを `3.42.0.0` と説明しているが、`pom.xml` はアプリバージョン `0.13.0`、SQLite JDBC `3.53.4.0`。READMEには存在しない `docs/DESIGN.md` への言及もある | バージョン、ファイル構成、起動方法、ウィンドウ仕様を実装から再確認し、リリース時に更新する |
| 高 | 開発指示書の陳腐化 | `.github/copilot-instructions.md` は「テストなし」「CIなし」「JavaFX 21」と記載しているが、JUnitテスト、GitHub Actions、JavaFX `26.0.2` が存在する | 指示書を現行構成へ更新し、古い記述が開発判断を誤らせないようにする |
| 中 | CIトリガー範囲 | `.github/workflows/ci.yml` は `push` のみで、`pull_request` が明示されていない | `pull_request` でも同じ検証を実行し、レビュー前にビルド失敗を検出する |
| 中 | UIの自動検証不足 | 現在のテストは設定、バックアップ、ファイル入出力、入力検証が中心で、JavaFX画面の構築・操作・ショートカット・テーマ切替を検証していない | ヘッドレスで可能なViewModel/サービス層のテストを追加し、GUI環境では起動 smoke test を別ジョブとして実施する |
| 中 | バージョン更新の自動化 | Dependabotは依存関係を更新するが、JavaFXやSQLiteの互換性確認はビルド成功だけに依存している | 主要依存関係の更新時にテストとパッケージ作成を必須化し、更新方針を記録する |
| 低 | `test-app.sh` の実用性 | スクリプトは実際のテストを実行せず、古いJAR名と画面イメージを表示するだけ | 実際に `mvnw` / `mvnw.cmd` の検証を実行するスクリプトに置き換えるか、参考資料として明確に位置付ける |

## 推奨する着手順

1. READMEと `.github/copilot-instructions.md` の事実関係を現行コードへ合わせる。
2. インポートをトランザクション化し、バックアップ・復元を一時ファイルと検証付きの原子的処理へ変更する。
3. DB処理をUIスレッドから分離し、大量データ時のページングまたはストリーム処理を検討する。
4. `pull_request` CIと、サービス層・画面境界の回帰テストを追加する。
5. メインクラスを責務別に分割し、バージョンと日時処理を一元化・現行API化する。
